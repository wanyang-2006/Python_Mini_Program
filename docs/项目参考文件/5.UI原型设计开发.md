## UI 原型设计开发

正常情况下，如果是比较小的、网页项目，可以直接利用 AI 生成前端一把梭。

但是由于小程序开发比网页开发又更多的复杂度和兼容性的问题，建议我们先利用 AI 单独开发出一套 HTML 网页版的原型图，人工确认之后，再把原型图代码发给 AI，继续开发小程序的前端，会更稳定一些。

UI 原型设计工具的选择：你可以考虑使用如 Figma、Sketch 或 Adobe XD 这样的专业工具来创建UI原型。这些工具不仅提供了丰富的设计资源，还支持团队协作。

但是现在有了 AI，直接让 AI 生成 HTML 格式的原型即可，就类似于让 AI 开发一个纯前端的网站。

UI 原型设计开发是一个相对独立的任务，我们可以搞个 **赛马** ，让不同的AI工具生成原型图，确保给每个工具提供相同的输入（比如功能需求、样式指南等）。然后选定最佳方案，再人工修改，直到获得一份纯前端的、满意的 UI 原型。

下面我们同时用 Claude Code、GitHub Copilot 开发。

### 为什么要先做 HTML 原型，而不是直接开发小程序？

这是本节最核心的策略，值得专门理解一下。小程序开发比普通网页多了不少兼容性和复杂度，如果让 AI 一上来就直接写小程序，出了问题很难定位是「UI 设计问题」还是「小程序兼容问题」。

所以教程采用了「分两步走」的策略：

```
第一步：用 AI 做纯 HTML 网页原型 → 人工确认 UI 满意
第二步：把确认好的原型代码发给 AI → 让 AI 照着开发小程序前端
```

好处是：

- HTML 原型在浏览器里就能看，改起来快、所见即所得
- 把「设计 UI」和「实现小程序」两件事解耦，每一步都更可控
- 原型确认后再开发，AI 有了明确参照，还原度更高、返工更少

### 什么是「赛马」开发？

我提到搞一个「赛马」，这是 AI 编程里很实用的一招： **同一个任务，同时让多个 AI 工具/模型去做，再挑最好的那个。**

 =

| 要点 | 说明 |
| --- | --- |
| 相同输入 | 给每个工具完全一样的需求、风格要求，保证可比性 |
| 并行产出 | 让它们各自出一版初稿，再各给一次修改机会 |
| 择优组合 | 选出最满意的方案，甚至可以结合多个方案的优点 |

本节就同时用了 Claude Code 和 GitHub Copilot 两套工具赛马，最后取两者之长。AI 生成有随机性，单押一个不一定出好结果，赛马能显著提高拿到满意方案的概率。

#### 为什么给 Claude Code 接国内大模型？

Claude Code 默认用的是 Anthropic 官方的国外大模型，国内直接用会有两个问题：网络访问不稳定、官方按量付费成本较高。

接入国内大模型（比如智谱 GLM）后，相当于「壳子用 Claude Code，引擎换成国产模型」：

- 网络更稳定，不用折腾代理
- 国产模型有编程套餐，性价比高
- Claude Code 强大的工具调用、文件操作能力照样能用

> 💡 这种「换大模型后端」的玩法在 AI 编程圈很常见，本质是利用 GLM 等模型提供的「OpenAI / Anthropic 兼容接口」。后面方案里 DeepSeek 也是用同样的兼容方式接入 LangChain 的，理解了一处，处处通用。

#### 怎么给 AI 描述「想要的 UI 风格」？

描述 UI 风格是新手最头疼的事 —— 脑子里有感觉，却说不出专业术语。我用了一个很妙的办法： **用一个大家都熟悉的「意象」来传达风格** ，比如「根据《漫画阿衰》这本书的意境来理解我想要的 UI 风格」。

这样做的好处是：

- AI 能联想到这个作品的整体调性（轻松、接地气、卡通、活泼）
- 比堆砌「橙黄色、圆角、卡通」这些零散词汇更立体
- 不需要你懂设计术语，用生活化的参照就行

除了「意象法」，我还用了另一招： **让 AI 先联网搜索同类产品的设计风格做参考** 。两招结合，就能把模糊的审美需求，转化成 AI 能理解的具体方向。

### 给 AI 反馈 UI 问题的技巧

观察上面两个工具的开发过程，会发现一个高效的反馈套路： **先肯定对的，再精准指出问题，最后给出方向。** 比如：

```
业务流程、功能和布局都是正确的（先肯定）
→ 但是字体和配色很奇怪，不利于阅读（指问题）
→ 请重构整套 UI 的配色和字体，可以用 SVG 画卡通形象（给方向）
```

这样反馈的好处：

- 先肯定对的部分，AI 不会把已经做好的地方推翻重做
- 问题描述具体（「配色单调」「阴影太重」「文字太密」），AI 才好改
- 给出方向而非空泛要求，避免 AI 瞎猜

> 💡 改 UI 是个反复迭代的过程，没有一次到位的。关键是每一轮反馈都要「具体 + 有方向」，把模糊的「不好看」翻译成 AI 能执行的具体调整项。

#### 几个高频实用技巧

深度优化环节信息量很大，把里面散落的实战技巧归纳一下，都是后面会反复用到的：

 = =

| 技巧 | 作用 |
| --- | --- |
| 先加 Git 版本控制 | 改坏了能随时回退到之前的版本，AI 编程的「后悔药」 |
| 在截图上做标注 | 改动点多时，直接在图上圈出来比用文字描述更精准 |
| 「只改 A，不要动 B」 | 明确限定修改范围，防止 AI 顺手把别的地方改坏 |
| F12 人工微调再回喂 | AI 实在改不对，自己用浏览器控制台调好，再把代码发给它参考 |
| 关注上下文用量 | 快满时主动保存代码、沉淀文档，避免 AI「断片儿」 |

> 💡 其中「先加 Git 版本控制」尤其重要。AI 编程经常会改出新问题，有了 Git，任何一次改动都能回退，相当于给整个开发过程上了保险。这也是为什么教程会在正式大改之前，专门让 AI 先做一次初始提交。
