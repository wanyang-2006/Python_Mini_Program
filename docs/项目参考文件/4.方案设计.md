### AI 死循环了怎么办？

AI 可能会「死循环」，也就是反复纠结、来回修改却出不了结果。这是 AI 编程里很常见的现象，记住一套通用的破解办法：

```
删掉当前对话 → 新开一个干净的对话 → 把关键文档（需求、方案输出计划）重新喂给 AI → 必要时换一个大模型
```

为什么有效？因为 AI 死循环往往是上下文被污染、或者钻进了某个错误的思路出不来。重开对话相当于「重启大脑」，再配合换模型，绝大多数死循环都能解决。这个技巧后面开发环节还会反复用到。

#### 为什么最后选了 Taro 而不是 AI 推荐的 uni-app？

这是本节一个非常值得学习的决策点： **AI 推荐的不一定是最适合你的，要结合自己的实际情况判断。**

AI 一开始推荐 uni-app，理由也很充分（中文友好、生态成熟）。但教程作者凭经验发现一个关键问题——uni-app 和它自家的 HBuilderX IDE 绑定很深，很多操作要在图形界面里点。而我们这个项目是 **让 AI 来主导开发** 的，AI 的强项是敲命令行，不擅长帮你点图形界面。



| 框架 | 和 AI 协作的契合度 |
| --- | --- |
| uni-app | 依赖自家 IDE 的图形界面操作，AI 不好接手 |
| Taro | 纯命令行脚手架 + 标准 React 写法，AI 上手快 |

所以最终改成了 Taro。这个例子说明： **做技术选型时，除了看框架本身好不好，还要看它和你的「开发方式」（这里是 AI 编程）合不合得来。**

### AI 大模型技术选型

优先选择国产大模型，DeepSeek、智谱 GLM、Kimi、阿里 Qwen 都可以。

选择 DeepSeek 是因为相对主流，尤其是国外的开发框架（比如 LangChain）对 DeepSeek 的接入更好一些；而且 [DeepSeek 开放平台](https://platform.deepseek.com/) 的文档也比较简单，适合新手学习。

MVP 推荐：

- 首选： `deepseek-chat`
- 预留： `deepseek-reasoner`

AI 给出的推荐理由：

1. 出题与报告生成更关注稳定输出和成本平衡。
2. `deepseek-chat` 更适合标准化内容生成。
3. `deepseek-reasoner` 可作为高难题或复杂分析的后续增强能力，而不是 MVP 必需项。

#### chat 模型和 reasoner 模型怎么选？

DeepSeek 提供了两种模型，理解它们的区别有助于做出合理选择：



| 模型 | 特点 | 适合场景 |
| --- | --- | --- |
| deepseek-chat | 响应快、成本低、输出稳定 | 标准化内容生成（出题、报告） |
| deepseek-reasoner | 会「思考推理」、能力更强、成本更高、更慢 | 高难度题目、复杂分析 |

本项目 MVP 阶段选 chat 作为主力，因为出题和生成报告更看重「稳定 + 便宜 + 快」，而不是极致的推理能力。reasoner 先预留着，等真的遇到需要深度推理的场景再用。这种「主力用便宜稳定的，难活儿留给强模型」的搭配思路，在实际项目里很常见。

### 前端技术栈

- 框架： `Taro 4.x`
- 视图库： `React 18`
- 语言： `TypeScript`
- 状态管理：优先轻量方案，MVP 可使用 `Zustand` 或页面内状态
- 请求库：基于 `Taro.request` 的统一封装，或使用兼容良好的轻量请求层
- UI 策略：优先自定义轻量组件，不在 MVP 引入过重 UI 框架
- 构建工具： `Taro CLI + VSCode + 微信开发者工具`

### 后端技术栈

- Web 框架： `FastAPI`
- 运行环境： `Python 3.11+`
- 数据校验： `Pydantic v2`
- HTTP 客户端： `OpenAI SDK` 兼容 DeepSeek API
- Prompt 编排： `LangChain` ，但仅用于模板化和输出约束，不做重型 Agent 化
- 配置管理： `pydantic-settings`
- 日志： `structlog` 或标准 logging
- 测试： `pytest`

为什么选 FastAPI？

1. 参数校验与文档能力强，适合快速定义 AI 接口。
2. 天然生成 OpenAPI 文档，便于前后端并行联调。
3. 异步友好，后续接入解析任务、异步报告生成更平滑。
4. 对单人开发效率很高，工程心智负担低于传统框架组合。

#### 什么是 LangChain？为什么选 LangChain？

[LangChain](https://github.com/langchain-ai/langchain) 是开源的 AI 开发框架，能够更好地对接 AI 大模型，实现各种复杂的 AI 应用所需的功能。

LangChain 主语言是 Python，同时网上有 JavaScript 和 Java 版本的（LangChain4j），核心思路都是类似的，会一个，其他语言的自然就会了。

结合 [LangChain 官方文档](https://docs.langchain.) ，本项目应当把 LangChain 作为 DeepSeek 的正式接入层，而不是仅作为可选辅助库。

推荐原因：

1. LangChain 官方推荐使用 `` 组织系统消息和用户消息，这比拼接长字符串 Prompt 更稳定、更易维护。
2. LangChain 官方提供结构化输出能力，可以直接把模型返回结果约束到 `Pydantic` Schema，适合本项目的题库 JSON 和报告 JSON 场景。
3. `langchain-openai` 的 `ChatOpenAI` 支持通过 `base_url` 和 `api_key` 对接 OpenAI 兼容接口，因此可以直接接 DeepSeek。
4. 把模型调用统一放在 LangChain 层，后续切换模型、增加重试、增加输出解析和引入 RAG 时，扩展路径更清晰。

使用边界也需要明确：

1. MVP 中使用 LangChain 的 `` 、 `ChatOpenAI` 、 `with_structured_output()` 。
2. 不在首版引入 Agent、复杂工具调用、LangGraph 或重型 RAG 编排。
3. LangChain 是正式编排层，但仍要保留清晰的服务层与异常处理，不能把所有逻辑堆进链定义中。

结论是： **LangChain 是本项目对接 DeepSeek 的正式方案，但首版仅使用其稳定的 Prompt 与结构化输出能力。**

#### 不用 LangChain 直接调 API 不行吗？

新手可能会问：直接用 OpenAI SDK 调 DeepSeek 不就行了，为什么还要套一层 LangChain？关键在于 LangChain 提供了两个对 AI 应用很重要的能力：

- 结构化输出（ `with_structured_output()` ）：本项目要 AI 返回严格的题库 JSON、报告 JSON，直接调 API 经常返回格式不对的内容；LangChain 能把输出约束到指定的数据结构，大大减少解析报错。
- 统一编排层：以后想换模型、加重试、接 RAG，只要改 LangChain 这一层，业务代码不用动。

> 💡 注意我强调的「使用边界」：MVP 阶段只用 LangChain 最稳的几个能力（Prompt 模板 + 结构化输出），不引入 Agent、LangGraph 这些重型功能。这是一种很克制、很务实的用法，避免一上来就把架构搞复杂。

### 其他技术选型

后续要扩展功能的时候，还要进行数据库、对象存储、搜索 API、部署上线等技术的选型，暂时先不考虑。

### Prompt 提示词

对于 AI 应用开发项目来说，提示词是非常重要的，我们这个项目要让 AI 生成题目关卡和用户的答题报告等。

更多提示词的设计技巧，看这篇文章： [https://ai.codefather.](https://ai.codefather.)

举个例子，比如出题的提示词：

```markdown
你是一名专业的 AI 学习教练，请根据用户提供的学习内容生成一组用于小程序闯关答题的题目。

要求：
1. 输出必须是合法 JSON，不要输出任何 JSON 之外的内容。
2. 题目总数为 5 题。
3. 题型包含：3 道单选题、1 道多选题、1 道判断题。
4. 每道题必须包含：题目编号、题型、题干、选项、正确答案、详细讲解、知识点标签、难度。
5. 讲解必须适合初学者阅读，避免过度学术化。
6. 如果用户输入内容过短，可以基于常识进行合理补充，但不要偏离主题。

JSON 输出结构示例：
{
 "title": "学习主题",
 "summary": "本次题库的主题摘要",
 "questions": [
 {
 "id": "q1",
 "type": "single",
 "stem": "题干",
 "options": [
 {"key": "A", "text": "选项A"},
 {"key": "B", "text": "选项B"}
 ],
 "answer": ["A"],
 "explanation": "详细讲解",
 "knowledge_point": "知识点",
 "difficulty": "easy"
 }
 ]
}

用户学习内容如下：
{user_input}
```

#### 出题 Prompt 的设计思路

这条提示词是整个项目的「灵魂」，AI 出题的质量好不好，全看它写得好不好。可以从中提炼几个通用的 Prompt 设计技巧：

 = =

| 技巧 | 在这条 Prompt 里的体现 |
| --- | --- |
| 设定角色 | 开头「你是一名专业的 AI 学习教练」，让 AI 进入正确的语境 |
| 明确约束 | 规定题目数量、题型分布、每题必含字段，输出可控 |
| 强制格式 | 「输出必须是合法 JSON，不要输出任何 JSON 之外的内容」 |
| 给出范例 | 直接提供 JSON 结构示例，AI 照着填，出错率大幅降低 |
| 处理边界 | 「输入过短可基于常识补充，但不要偏离主题」，提前堵住异常情况 |
| 预留变量 | 末尾用 `{user_input}` 占位，配合 LangChain 模板动态填入 |

> 💡 「设定角色 + 明确约束 + 强制格式 + 给出范例」是写好结构化输出 Prompt 的黄金组合，做任何 AI 应用都能套用。

### 核心开发流程

正确的 MVP 实现顺序应该是：

1. 先把后端 `生成题库接口` 跑通。
2. 再做前端闯关页面。
3. 再做报告生成接口。
4. 最后把首页接入，形成端到端闭环。

而不是一开始就做：

1. 用户系统
2. 数据库
3. 分享海报
4. 多端适配细节

#### 为什么开发顺序这么排？

这个开发顺序背后是 MVP 思想的具体落地： **先打通「核心价值链路」，把锦上添花的东西往后放。**

本项目的核心价值链路是：

```
用户输入知识 → AI 生成题目 → 用户答题闯关 → AI 生成报告
```

只要这条链路能跑通，产品就「活」了，能拿去验证、能演示。而用户系统、数据库、分享海报这些，虽然重要，但都是「核心链路之外」的支撑功能：

- 没有用户系统，照样能体验完整的答题流程
- 没有数据库，可以先把数据放内存里跑通逻辑
- 分享海报、多端适配，更是上线前才需要打磨的细节

> 💡 一个反直觉但很重要的经验： **别一上来就做用户登录注册。** 登录注册要依赖数据库、第三方授权，又复杂又不产生核心价值，很多新手卡在这里就放弃了。先把最能体现产品价值的功能跑通，成就感和正反馈会推着你继续走下去。
