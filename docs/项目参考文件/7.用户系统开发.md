#### 为什么核心功能跑通后才做用户系统？

回顾第 4 期方案设计强调的开发顺序：先跑核心链路，用户系统这种支撑功能往后放。现在核心流程通了，才轮到用户系统登场，原因很清晰：

- 用户系统依赖数据库、第三方授权，又复杂又不直接产生核心价值
- 先把「能用」的产品做出来，再补「账号体系」，节奏更稳、成就感更强

而做用户系统的直接动因也很务实：

 =

| 不做用户系统的问题 | 用户系统怎么解决 |
| --- | --- |
| 任何人都能白嫖调用 AI，有刷 Tokens 的风险 | 登录后才能用，能识别和限制用户 |
| 无法保存用户的闯关记录 | 登录后数据和用户绑定，可持久化 |
| 看不到个人学习情况 | 有了账号才能做个人中心、积分等 |

#### 大功能拆批次、排优先级

这里有个很重要的协作技巧： **功能多的时候，让 AI 分批次、排优先级，而不是一口气全做。**

为什么？因为一次塞太多功能给 AI，容易上下文不够、做着做着就断片儿。合理的做法是：

```
先做用户登录（最基础）→ 再做获取用户信息 → 再做闯关历史列表 → ……
```

而且我还让 AI「把本次功能的需求分析文档单独保存为一个新文档」，这同样是为了对抗断片儿——把每个大功能的需求沉淀成独立文档，AI 忘了就重新喂给它。这与前面「需求文档当记忆锚点」的思路一脉相承。

#### 为什么把 SQLite 换成 MySQL？

AI 一开始默认用了 SQLite（内存数据库），但教程作者人工把它改成了 MySQL。这是一个典型的「人工凭经验纠正 AI 选型」的例子。两者的区别：

 = =

| 维度 | SQLite | |
| --- | --- | --- |
| 形态 | 轻量、单文件/内存，零配置 | 独立的数据库服务，需要安装 |
| 数据持久性 | 用内存模式时，重启可能丢数据 | 数据稳定持久化 |
| 适合场景 | demo、极小数据量、快速测试 | 正式业务、关系复杂、长期演进 |

用户、闯关记录、答题记录、报告之间有大量关联关系，未来还要扩展错题本、排行榜等，关系会越来越复杂——这正是 MySQL 这种关系型数据库擅长的。所以即便当前数据量不大，也应该一步到位选 MySQL，因为 **用户系统是「基础设施」，要为未来扩展留余地。**

#### 看懂微信静默登录 + JWT 鉴权

这套登录方案是小程序用户系统的标准做法，理解它对以后做小程序很有帮助。

微信静默登录的流程，可以简化理解为：

```
用户打开小程序 → 前端拿到微信临时 code → 发给后端
→ 后端用 code + AppID + AppSecret 向微信服务器换取 open_id
→ open_id 唯一标识这个微信用户 → 后端据此创建/查找用户
```

整个过程用户「无感」，不需要点任何按钮，体验很好。换到 open\_id 后，再用 JWT 完成后续的登录态维持：



| 概念 | 一句话理解 |
| --- | --- |
| open\_id | 一个用户在某个小程序里的唯一身份证号 |
| JWT | 登录成功后发给前端的「令牌」，之后每次请求带上它，后端就知道你是谁、是否已登录 |

> 💡 JWT（JSON Web Token）是目前最主流的鉴权方案：后端校验登录成功后，签发一个加密令牌给前端，前端把它存起来，后续请求都带上。后端只要验证令牌有效，就认你已登录，不用每次都查数据库密码。

💡 数据库的「建表」到底在干嘛？

建表就像「你有一个 Excel 表格，要先定义好表格的列结构，才能往里面写数据」。

具体来说：

- 建表（建 Schema）：定义有哪些表、每张表有哪些字段（列）、字段是什么类型，比如 `user` 表有 `id` 、 `open_id` 、 `nickname` 、 `avatar` 等列

我让 AI 把建表的 SQL 语句保存成单独文件，好处是：

```
SQL 建表语句存成文件 → 即使 AI 断片儿，重新读这个文件就能立刻找回完整的表结构
```

这又是「对抗 AI 断片儿、沉淀关键信息」的一个具体实践。数据库结构是项目的骨架，单独存档非常有必要。

#### 2、微信小程序信息准备

如果要做真实的微信登录，这两项是必须的：

1. 小程序 `AppID`
2. 小程序 `AppSecret`

没有这两个值，没法实现真实的 `code2session` 登录链路。

如果没有在微信开发者工具中登录，微信小程序在“游客模式”下无法获取到 AppID 和 AppSecret。

正常情况下，你需要到微信公众平台注册小程序，但是要填写信息，比较麻烦。

所以我们可以申请一个测试号，来更方便地测试小程序。

参考 [官方申请测试号的文档](https://developers.weixin.qq..html) ：

![](https://pic.code-nav.cn/course_picture/1608440217629360130/sHKP7n9Nr1pAEkvS.webp)

申请并登录后，获取到 AppID 和 AppSecret，千万不要泄露！

![](https://pic.code-nav.cn/course_picture/1608440217629360130/Ofln1RjnOhPLrpRK.webp)

我们要把这两个值填写到 `.env` 环境变量中，可以让 AI 先帮我们给环境变量文件增加这两个配置。而且应该让 AI 生成一个环境变量示例文件，这个文件是可以提交甚至开源的，这样别人拿到你的项目，就知道怎么根据示例文件进行配置。

```markdown
同时生成一个环境变量示例文件（不包含敏感信息），这个文件是可以提交甚至开源的，这样别人拿到项目，就知道怎么根据示例文件进行配置。
```

**为什么用「测试号」而不是正式注册小程序？**

做真实的微信登录，必须有 AppID 和 AppSecret 这两个值，它们是后端向微信服务器换取用户身份（ `code2session` ）的凭证。

但正式注册一个微信小程序要填一堆主体信息、走审核，比较麻烦。所以教程用了一个轻量的办法—— **申请测试号** ：



| 方式 | 特点 |
| --- | --- |
| 正式注册小程序 | 要填主体信息、审核，能上线，但准备成本高 |
| 申请测试号 | 几分钟就能拿到 AppID/AppSecret，专门用来开发测试 |

学习阶段用测试号就够了。同时注意我再次强调的安全规范：AppID、AppSecret 同样属于敏感信息，填进 `.env` 、绝不泄露，并配一个不含真实值的 `.env.example` 示例文件方便别人参照配置（这正是第 6 期讲过的做法）。

#### 扩展功能时的关键约束：别动现有功能

注意开发提示词里加了一条很重要的约束： **「只扩展功能，一定不要影响现有的核心功能」。**

这是迭代开发中极其关键的一条原则。因为 AI 在加新功能时，很可能顺手改动到已有代码，把原本好好的核心流程改坏。所以：

- 在提示词里明确划定边界：「只加新功能，别碰现有功能」
- 开发前已经用 Git 提交过，万一改坏了能回退
- 开发后要回归测试，确认老功能（出题、答题、报告）依然正常

这也呼应了 Bug 修复那一节会讲到的「回归测试」思想—— **新代码不能破坏旧功能，是专业开发的底线。**

#### 看懂微信小程序测试中的两个「正常报错」

这一节测试时遇到的几个报错，其实都是小程序开发的「常见正常现象」，不理解会被吓到，理解了就知道怎么处理：

 =

| 报错现象 | 原因 | 解决办法 |
| --- | --- | --- |
| 游客模式下登录失败 | 没填 AppID，拿不到微信身份 | 在开发者工具里改成测试号 AppID，并微信登录 |
| 请求域名不合法 | 后端是本地地址，没在微信白名单里 | 本地设置勾选「不校验合法域名」 |
| 页面加载异常 | 旧缓存残留 | 清理小程序缓存后重新编译 |

> 💡 「不校验合法域名」是本地开发阶段的临时手段。微信要求线上小程序的后端域名必须备案 + 配置到白名单，但我们本地没有线上服务器，所以先关掉校验方便调试。等真正上线时，还是要走正规的域名配置流程。
