### 2、集中修复 Bug

如果你不确‌定‌‌什么 Bug 算是好改的小 Bug，可以让 AI 帮؜你梳理。      ؜؜             ⁠⁠             0V81tesmfvZygD7AWg2Dy8rTk8qVC7yxJzF7922wv7w=

一般跟功能‌‌‌相关的（尤其是未完成的新功能），建议单独开发；其他的 UI ؜؜؜方面的优化、一些接口⁠⁠⁠调用的小错误，都可以一把梭。

为什么不一个个修复 Bug 呢？

1）这样可能会导致，你修完‌‌‌一个 Bug，验收完；然后修复第 2 个 Bug 之后，第一个 Bug 又出现了，可能会出现验收的遗漏。所以一般企业中的专业测试人员会写测试报告、测试؜؜؜用例，每次程序改动，会整体跑一遍测试，确保老的功能⁠⁠⁠不会因为新代码的改动而出现 Bug。0V81tesmfvZygD7AWg2Dy8rTk8qVC7yxJzF7922wv7w=

2）一个个‌‌‌修复 Bug，可能要多次输入相同的上下文，؜导致浪؜费 tok؜⁠ens⁠。

3）AI 能够并行执行任务，这样修复 Bug 更快。

怎么集中改‌‌‌呢？我们可以参考企业测试人员的思路，让 AI 生成测试؜؜؜报告，在开发人员集⁠⁠⁠中修复后，让程序自主验收。0V81tesmfvZygD7AWg2Dy8rTk8qVC7yxJzF7922wv7w=

由于我们在修复之前‌‌‌已经开发完成的功能的 Bug，如果之前的上下文空间还有 50% 及以上，那就不要新开上下文了，毕竟修复小 B؜؜؜ug 任务难度不大，还能复用之前的上⁠⁠⁠下文节约一些 tokens。

| 情况 | 应对办法 |
| --- | --- |
| AI 连续 2 次没解决同一问题 | 「施压」+ 要求重新分析逻辑（如「再给你一次机会，重新分析这块的前端逻辑」） |
| AI 信息不够 | 补充更详细的现象、预期、错误信息 |
| 某个 Bug 一直卡 | 单独拆出来当大 Bug，新开对话专门处理 |

「施压话术」看起‌‌来像‌玩梗（比如「再修不好就放弃项目」），但实际有时确实有效 —— 它相当于强调了任务的重要性，促؜؜使 AI 更认真地重新分析，而不⁠⁠是敷؜衍地重复之前的错误思路。            ⁠                    

> 💡 不过别滥用施压。最根本的办法还是「提供足够详细的信息」：现象 + 预期 + 错误信息越清楚，AI 第一次就改对的概率越高。施压只是兜底手段。
