#### 养成「开发前先提交」的习惯

注意这一节的开头就是「记得提交代码」，这不是随口一提，而是 AI 编程里非常重要的安全习惯。

AI 大段生成代码时，很可能改坏现有功能。如果开发前没有一个干净的提交点，出了问题就很难回退。养成习惯：

```
每完成一个阶段（原型、一个功能、一次大改）→ 立刻提交一次 Git
```

这样每个提交点都是一个「存档」，AI 把代码改乱了，随时能回到上一个正常版本。可以直接用自然语言让 AI 帮你提交，它会自动写好 commit 信息，比手敲命令更省事。

### 开发编码

编写给 AI 的提示词，注意事项：

1. 给出提供的资源
2. 必须阅读理解技术栈对应的最新文档
3. 完全还原 UI 原型
4. 可以让 AI 利用 TDD 或者浏览器操作（Browser Use）让 AI 写代码自行测试验证
```markdown

## 提供的资源

@需求分析文档
@方案设计文档
@UI原型图

## 需要完成的任务

请你帮我完成 MVP 核心功能的完整小程序前端 + Python 后端的开发

## 注意事项

1）你必须完整阅读理解我给你的所有资源，有任何不确定的地方必须及时找我人工确认，才能进行下一步
2）给出你具体要执行的开发步骤，找我人工确认后，再进行开发
3）对于方案设计中提到的技术栈（比如 Taro 和 LangChain），你必须通过 Context7 或者官方文档获取到最新的用法，确保编写的代码是正确的
4）UI 原型必须完全按照我提供的 UI 原型图来，不要自行发挥
5）你必须通过 TDD 自行测试所有的后端功能代码
```

#### 拆解这条开发提示词的「五要素」

这条开发提示词是整个项目最关键的指令之一，它的结构其实可以提炼成一套可复用的模板：

 =

| 要素 | 在提示词里的体现 | 作用 |
| --- | --- | --- |
| 角色设定 | 「你是专业的程序员和小程序开发者」 | 让 AI 进入正确语境 |
| 提供资源 | 需求分析、方案设计、UI 原型 | 给 AI 完整的上下文，防止它瞎猜 |
| 明确任务 | 完成 MVP 核心功能的前后端开发 | 目标清晰，不发散 |
| 先确认再动手 | 「给出开发步骤，人工确认后再开发」 | 关键节点留人工把关，避免跑偏 |
| 质量约束 | Context7 拿最新文档、完全还原原型、TDD 测试 | 给代码质量上多重保险 |

> 💡 「TDD」即测试驱动开发，让 AI 先写测试、再写功能代码，并用测试自动验证对错。配合前面装的 Playwright（Browser Use），AI 就能实现「写完自己测、有问题自己修」的闭环，大大减少人工来回沟通。

#### 用脚手架生成初始代码，比让 AI 手写更划算

这里藏着一个很实用的省钱省时技巧： **项目的初始化模板代码，用官方脚手架生成，别让 AI 一行行手写。**

原因很实在：

- 脚手架（如 `taro init` ）一行命令生成标准项目结构，又快又不会出错
- AI 手写这些模板代码，既慢又费 Tokens，还可能写出不标准的结构
- 把 Tokens 省下来，留给真正的业务逻辑开发更值

> 💡 进阶经验：你可以把脚手架生成的项目沉淀成自己的「项目模板」，以后做新项目直接基于老模板二次开发，能省下大量初始化的时间和 Tokens。这也是为什么有经验的开发者效率更高——他们手里有一堆现成的模板。

#### 为什么敏感配置要放.env 且不能提交？

`.env` 是专门存放敏感配置（API Key、数据库密码等）的环境变量文件。它的核心规矩就两条：

- 敏感信息只写在 `.env` 里，代码里通过读取环境变量来用，不要把 Key 硬编码在代码中
- `.env` 必须加入 `.gitignore` ， **绝对不能提交到 Git、更不能开源到 GitHub**

为什么这么强调？因为一旦把 API Key 提交到公开仓库，会被爬虫秒级扫到并盗用，轻则额度被刷光，重则产生大额扣费。

```
敏感信息 → 写进 .env（本地保存）
.env → 加入 .gitignore（不提交）
.env.example → 只留字段名、不留真实值（可以提交，方便别人参照配置）
```

后面用户系统那一节，就会让 AI 生成一个 `.env.example` 示例文件，正是这套做法的延续。

#### 什么是上下文「断片儿」？怎么应对？

我多次提到 AI「断片儿」，这是指：对话太长、上下文超出大模型容量（比如超过 20 万 token）时，工具会自动「压缩」前面的对话，导致 AI 忘掉之前的关键信息（比如忘了你还没填 API Key 就去测试了）。

应对断片儿的几个实用办法：

 = =

| 办法 | 说明 |
| --- | --- |
| 及时沉淀文档 | 把重要的需求、方案、数据库结构存成文件，断片后能重新喂给 AI |
| 关键代码及时提交 | 用 Git 保存进度，不怕上下文丢失 |
| 手动提供文档 | 别让 AI 自己联网抓一大堆文档（很占上下文），直接把关键文档贴给它 |
| 必要时新开对话 | 上下文太乱时，开新对话 + 重新提供文档，相当于「重启大脑」 |

> 💡 AI 断片了但已经跑了很久，可以先不打断，看看最终效果，能跑就行；实在跑不起来再换方式重来。不必追求过程完美，结果可用才是关键。

#### 如何高效地给 AI 报 Bug？

这一节的测试环节，演示了一套非常专业的「报 Bug 流程」，值得学起来。关键是： **给 AI 的信息越具体，修复越快。** 一条好的 Bug 描述应该包含：

 =

| 信息 | 例子 |
| --- | --- |
| 现象/操作 | 点击「开始生成题目」之后 |
| 错误信息 | 后端返回的完整报错 JSON（含 code、message） |
| 相关参数 | 请求参数（user\_input、question\_count 等） |

怎么拿到这些信息？教程演示了开发者工具的两个核心面板：

- Network（网络）面板：看请求有没有发出去、后端返回了什么。如果根本没发请求，说明是前端的问题。
- Console（控制台）面板：看前端代码报的错误信息。

> 💡 一个高效的排查思路：先看 Network 判断「问题在前端还是后端」——有请求且后端报错就是后端问题，没请求就是前端问题——再去对应的地方找详细报错。定位准了，AI 才能改得准。

### 什么是 Harness Engineering？

Harness Engineering（工程化）想表达的核心是： **AI 编程的稳定输出，靠的不是某一句神级提示词，而是前期一整套「工程化准备」。**

回顾一下我们前面做的所有铺垫：

```
需求分析文档 + 方案设计文档 + UI 原型 + MCP（Context7 拿最新文档）+ Skills + Git 版本控制 + 清晰的提示词
```

正是这些准备工作，给 AI 搭好了一套「脚手架/约束框架」（harness），所以即使中途上下文断片儿，AI 依然能生成几乎可用的完整代码。这也是整套教程想传递的核心理念： **与其纠结提示词技巧，不如把前期的工程化准备做扎实。**
